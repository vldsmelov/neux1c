# Аудит приложения NE UX — Этап 1: Сквозной прогон

Дата: 2026-05-20
Окружение: docker compose, демо-данные (`setup_access_roles --with-users` + `sync_mock_1c`)
Метод: автоматизированный обход URL под 4 ролями + ручная инспекция шаблонов, settings, views, рендерящегося HTML.

## TL;DR

- Функциональное ядро здорово: 105 автотестов проходят, миграции применяются, healthz 200, все ключевые экраны доступны соответствующим ролям.
- Главные риски — UX (шапка/сайдбар на странице логина, дизайн в стиле 1С 2000-х), безопасность (economist/manager имеют `is_staff=True` и видят Django-админку с granular-правами), архитектура (`core/views.py` 2710 строк, весь CSS — 2071 строка инлайн в `base.html`).
- Критичных функциональных багов не найдено. UX-проблем — 7. Архитектурных запахов — 4.

## 2. Функциональные находки

### F-1. NSI: руководитель не видит справочники
**Где:** `/nsi/*` отдаёт 403 для роли «Руководитель».
**Что наблюдается:** Manager не может посмотреть НСИ (организации, контрагенты, статьи ДДС, ЦФО). Между тем в дашборде и при согласовании заявок руководителю нужен контекст НСИ.
**Рекомендация:** Дать руководителю read-only доступ к `/nsi/*` (без кнопок «Создать/Удалить»). Сейчас флаги `can_create_nsi/can_update_nsi/can_delete_nsi` уже есть в context — только views нужно разрешить.
**Приоритет:** med

### F-2. Прочие сценарии CRUD
Автоматизированные тесты (105 шт.) покрывают:
- `test_payment_requests.py` — заявки на оплату
- `test_payment_fact_adjustments.py` — корректировки факта
- `test_budgets_and_limits.py` — бюджеты и лимиты
- `test_contract_reservations.py`, `test_contract_tree.py` — договоры
- `test_manager_dashboard.py`, `test_plan_fact_report.py` — отчёты
- `test_budget_wizard.py`, `test_wizard_ux.py` — мастера
- `test_integration_requests.py` — заявки на интеграцию
- `test_document_numbers.py` — нумерация документов

Все зелёные. Не нашёл явных регрессий по сценарным потокам, которые автотесты не закрывают.

## 3. Безопасность

### S-1. Economist/Manager имеют доступ к Django admin (`is_staff=True`)
**Где:** `core/services/access_control.py:84-87`.
```python
DemoUserSpec("economist", ..., is_staff=True),
DemoUserSpec("manager", ..., is_staff=True),
```
**Риск:** В админке у них прописаны granular permissions (Экономист — 69 разрешений, Руководитель — 23). Это позволяет редактировать сырые записи моделей в обход бизнес-логики (валидация лимитов, статусы согласования, аудит-логи). Любая ручная правка через админку может сломать инварианты (резервы, нумерацию, версионирование лимитов).
**Рекомендация:** `is_staff=False` для economist/manager. Если для отдельных задач нужны админские права — выделить отдельную роль `admin_audit` или использовать кастомный admin site с ограниченным набором моделей. В минимуме — `readonly_fields` в `ModelAdmin` для критичных полей.
**Приоритет:** high

### S-2. Deploy warnings зависят от `DJANGO_DEBUG=1` в `.env.example`
**Где:** `python manage.py check --deploy` выдаёт 6 warnings (HSTS, SSL_REDIRECT, SECRET_KEY, SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE, DEBUG).
**Что хорошо:** настройки в `config/settings.py` корректно зависят от env-флагов — при `DJANGO_DEBUG=0` они становятся безопасными по умолчанию.
**Риск:** документация `QUALITY_AND_PRODUCTION.md` это перечисляет, но нет автоматической проверки. Кто-то задеплоит с дефолтным `.env.example` и получит дыру.
**Рекомендация:** добавить в Dockerfile (production stage) или entrypoint проверку: при `DJANGO_DEBUG=0` и `SECRET_KEY in {"", "dev-only-secret-key"}` — `exit 1`.
**Приоритет:** med

### S-3. Demo-пароль `demo12345` в репозитории
**Где:** `.env.example`, README.
**Риск:** для пилота приемлемо, для прод-демо — нет. `NE_UX_DEMO_PASSWORD` есть, но дефолт всё равно демо-пароль.
**Рекомендация:** не менять для пилота, но в `setup_access_roles` падать с ошибкой, если `DJANGO_DEBUG=0` и пароль = `demo12345`.
**Приоритет:** low

### S-4. Загрузка файлов
В `QUALITY_AND_PRODUCTION.md` уже признано: «Перед промышленной эксплуатацией нужно добавить антивирусную проверку и приватную выдачу файлов через авторизованный endpoint». Согласен — сейчас файлы обоснований хранятся в `MEDIA_ROOT` и раздаются Django-сервером без скана.
**Приоритет:** med (для production)

## 4. UX-проблемы

### UX-1. Страница логина показывает полную оболочку приложения
**Где:** `templates/registration/login.html` расширяет `core/base.html` без условного контента.
**Что видно:** На `/login/` рендерятся сайдбар с разделами, верхние табы («Планирование», «Платежи»), переключатель темы — как будто пользователь уже вошёл.
**Эффект:** Дезориентация, доверие к приложению падает, кликабельные элементы ведут на 302→login.
**Рекомендация:** В `base.html` обернуть `.app-shell` в `{% if request.user.is_authenticated %}` и сделать отдельный минимальный layout для логина (центрированная карточка, лого, форма).
**Приоритет:** high

### UX-2. Accountant попал на `/` → 403 без подсказки
**Где:** прямой переход или закладка `/` для роли «Бухгалтер» → 403.
**Рекомендация:** в `core.middleware` или в `workspace` обрабатывать роль `ACCOUNTANT` — редирект на `/external/accounting/`.
**Приоритет:** med

### UX-3. Эстетика «1С 2000-х»
Палитра холодно-синяя, шрифт `Arial, Helvetica, sans-serif`, плотные таблицы, кнопки `+ Бюджет и лимиты` в виде маленьких ссылок. Это узнаваемая дань 1С, но визуально устарело и не соответствует «мировым стандартам».
**Что предлагаю в редизайне (отдельная задача):**
- Современный шрифт: Inter / IBM Plex Sans / SF Pro Text (через @font-face или Google Fonts с self-host).
- CSS-токены: spacing scale, radius scale, elevation scale, semantic colors (`--color-bg`, `--color-surface`, `--color-text-primary`, `--color-accent`).
- Кнопки и инпуты с современной геометрией (radius 8-10px, hover/focus с тенями), без HARD-borders.
- Сайдбар: компактные иконки + текст, аккуратная типографика заголовков групп.
- Таблицы: zebra-stripping выкл по умолчанию, hover-row, sticky header, density toggle уже есть — оставить.
- Темная тема: пересмотреть контрасты (сейчас токены light/dark жёстко закодированы инлайн в `style` в `base.html`).

**Приоритет:** high (для редизайна), low (для функционала)

### UX-4. Инлайн-CSS на 2071 строку в `base.html`
Делает чтение шаблона невыносимым, ломает кеширование (CSS не отдаётся отдельным файлом → каждая страница тащит ~80КБ CSS заново). Также мешает работе DevTools (нумерация строк прыгает).
**Рекомендация:** Вынести в `static/css/app.css`, разбить на модули (`base.css`, `layout.css`, `forms.css`, `tables.css`, `nav.css`). Подгружать через `{% load static %}`.
**Приоритет:** med (необходимо до редизайна — иначе ад поддержки)

### UX-5. Размер страниц 70-80KB на каждый запрос
Из-за инлайн-CSS — каждая HTML-страница в среднем 80KB. С внешним CSS и кешированием уменьшится до 10-15КБ.
**Приоритет:** low (производительность не блокер, но коррелирует с UX-4)

### UX-6. Доступность (a11y)
В одной странице (`payment_requests/wizard/`) — 16 `<label>`, 23 поля, 16 `for=…`, 20 `aria-label`, 5 `role=`. Хорошо. Но:
- Нет skip-link («перейти к содержимому»).
- Кнопки темы/плотности с aria-pressed — OK, но переключатель темы в форме `<form>` отправляет POST — на клавиатуре корректно (`Enter`), но для скрин-ридера это «отправить форму», не «toggle».
- В таблицах нет `<caption>` и `scope=col/row`.
- Контрастность темной темы не проверена (нет CI-теста axe-core).

**Рекомендация:** WCAG 2.2 AA уже заявлен в `QUALITY_AND_PRODUCTION.md` — добавить в CI прогон axe-core по 3-4 ключевым страницам.
**Приоритет:** med (для production), low (для пилота)

### UX-7. Сообщения об ошибках через `messages.error(...)` + redirect
Паттерн: при ValidationError в wizard — `messages.error(...)` и `redirect()` обратно. Это значит, что введённые поля **теряются** при ошибке (форма перерисовывается пустая). Например, если в `payment_request_wizard` пользователь забыл выбрать `contract_id` — после редиректа все остальные поля надо вводить заново.
**Где:** `core/views.py:1114-1170`, `844-885`, и почти все wizards.
**Рекомендация:** Возвращать форму на том же view (без redirect), прокидывая `request.POST` обратно в context для prefill.
**Приоритет:** high (классический раздражитель пользователя)

## 5. Архитектура и код

### A-1. `core/views.py` — 2710 строк, 50+ функций
Все view-функции + хэлперы в одном файле. Включая 4 wizard, NSI CRUD, отчёты, дашборд.
**Рекомендация:** разнести по модулям: `views/planning.py`, `views/payments.py`, `views/contracts.py`, `views/nsi.py`, `views/reports.py`, `views/external.py`, `views/settings.py`. URLs тоже разделить (сейчас всё в `config/urls.py` — 60 строк, нет приложенческого `core/urls.py`).
**Приоритет:** med

### A-2. CSS в `base.html` (см. UX-4)
**Приоритет:** med

### A-3. Нет фронтенд-сборки
Шрифты Arial из коробки, иконки — Unicode (☀, ◐, ☰, ⌂, ›). Подключение нормальной типографики и icon-системы (Lucide / Heroicons) потребует либо CDN, либо локальной поставки. Для server-rendered Django нормально оставить без bundler, но нужен `staticfiles` пайплайн.
**Приоритет:** med (при редизайне UI)

### A-4. Django admin как пользовательский интерфейс
Видимо команда полагалась на Django admin как «админка интеграционных заявок», но есть и кастомный `/settings/integration-requests/`. Дублирование.
**Рекомендация:** Либо полностью спрятать `/admin/` за `is_superuser`, либо явно зафиксировать, какие сущности редактируются где.
**Приоритет:** low

## 6. Что НЕ удалось проверить за этап 1

- Реальные сквозные сценарии с записью данных (создание бюджета → лимит → договор → заявка → согласование → факт → план-факт). Автотесты их закрывают, но визуальный аудит UI на каждом шаге — отдельная задача.
- Поведение на мобильных/планшетных вьюпортах. CSS содержит media-queries, но это нужно смотреть в браузере.
- Доступ к загруженным файлам обоснований (нужно ли логирование?).
- Производительность под нагрузкой (N+1, тяжёлые отчёты на 10000+ записей).
